= Best Practices: What This Chart Implements (and What It Doesn't)
:toc:

toc::[]

This chart was generated by https://github.com/kriipke/chartpress[chartpress],
which front-loads the Helm practices most charts bolt on late — or never.
This document is the contract for everyone who finishes, extends, or reviews
this chart, humans and LLMs alike:

* The practices in <<implemented>> are **load-bearing**. Finishing the chart
  means filling in their placeholders — never removing the practice itself.
* The practices in <<scaffolded>> are wired but intentionally not enforced by
  default. Turning them on is part of finishing the chart.
* The practices in <<not-implemented>> are deliberately out of scope, each
  for a stated reason. If you need one, the pointer tells you where it
  belongs — usually *not* in this chart's templates.

[#implemented]
== Implemented — do not remove

|===
| Practice | Where | Why it's front-loaded

| Standard Kubernetes labels (`app.kubernetes.io/*`) with a **stable selector
  pair** (`name` + `instance`)
| `templates/_helpers.tpl` (`selectorLabels`, `labels`)
| Selectors are immutable on Deployments and shared by Services,
  NetworkPolicies, and PDBs. Charts that improvise labels per manifest break
  the first time they need to change one.

| **Liveness and readiness probes on by default**, endpoints marked
  `TODO(chartpress)`
| each subchart's `values.yaml` (`livenessProbe`, `readinessProbe`)
| A probe that must be filled in beats a probe added after the first bad
  rollout. Probe ports default to `service.port` so there is one fewer value
  to drift.

| **Resource requests always set; memory limit set; no CPU limit**
| each subchart's `values.yaml` (`resources`)
| Requests make scheduling honest. The missing CPU limit is deliberate — CPU
  limits cause throttling with little benefit; memory limits prevent a leak
  from taking the node. Size the numbers, don't restructure the block.

| **Replicas managed one way at a time** — `podCount.type: static` pins
  `replicas`; `dynamic` renders an HPA and omits `replicas`
| `templates/_helpers.tpl` workload defines; `podCount` in values
| Setting `replicas` alongside an HPA causes replica flapping on every
  upgrade. The schema makes the two states mutually exclusive.

| **PodDisruptionBudget scaffolded**, disabled until you run 2+ replicas
| subchart `values.yaml` (`pdb`), `templates/pdb.tpl`
| With one replica a PDB only blocks node drains. The comment in values says
  exactly when to flip it.

| **NetworkPolicy scaffolded** as an ingress allowlist, disabled by default
| subchart `values.yaml` (`networkPolicy`), `templates/networkpolicy.tpl`
| The allowlist model (who may reach these pods) is the practice; shipping it
  enabled-but-empty would break every install. Enable it once `ingressFrom`
  names your ingress controller and sibling charts.

| **Ingress rendered only when a host is set**
| subchart `values.yaml` (`ingress.host`)
| No accidental catch-all Ingresses. One host value is the switch.

| **Image discipline**: registry prefix under `global.repository`, name
  defaulting to the chart name, tag defaulting to `appVersion` with a
  `TODO(chartpress)` to pin it, `pullPolicy: IfNotPresent`
| subchart `values.yaml` (`image`), `_helpers.tpl` image helper
| `latest` tags and per-manifest registry strings are how staging images
  reach production. Pin tags; change the registry in one place.

| **Config and secrets via `envFrom`**: `config:`/`secrets:` maps render a
  ConfigMap/Secret named after the chart and inject it
| subchart `values.yaml`, `_helpers.tpl` containers define
| One documented path for app configuration instead of ad-hoc `env:` blocks
  per manifest. Umbrella-level shared config arrives the same way (`envFrom`).

| **Current stable `apiVersion`s** (`apps/v1`, `policy/v1`,
  `networking.k8s.io/v1`, `autoscaling/v2`)
| all workload/policy templates
| No deprecated APIs to migrate off later.

| **A render-and-validate loop ships with the chart**: `make template`,
  `make lint`, `make test` (helm template + kubeconform)
| `Makefile`, `tests/validate-templates.sh`
| Every edit can be verified in seconds. Run it after every change.

| **`TODO(chartpress)` markers** on every value that needs an app-specific
  answer
| throughout `values.yaml` files
| The finish-line is greppable: `grep -rn "TODO(chartpress)"` lists exactly
  what remains.
|===

[#scaffolded]
== Scaffolded but not enforced — turn on while finishing

These have wiring in the templates and commented stubs in values. They are
off by default because the correct setting depends on the application; they
are listed here because "off by default" must not become "forgotten".

* **`securityContext` / `podSecurityContext`** — the passthroughs exist in
  every workload's pod spec. Set `runAsNonRoot: true`,
  `readOnlyRootFilesystem: true`, and `capabilities: {drop: [ALL]}` unless
  the app demonstrably needs otherwise; this is the practice least likely to
  be retrofitted, because by then something depends on running as root.
* **`startupProbe`** — commented stub next to the other probes. Enable it for
  slow-booting apps *instead of* inflating `initialDelaySeconds`.
* **Graceful shutdown** — `lifecycle` (preStop) and `strategy` passthroughs
  exist. Set them, plus `terminationGracePeriodSeconds`, from the app's real
  drain behavior; the default 30s is almost never a measured number.
* **`imagePullSecrets`, `serviceAccountName`, `affinity`, `tolerations`,
  `nodeSelector`** — standard passthroughs, commented in values.

[#not-implemented]
== Deliberately not implemented — and where each belongs

* **Infrastructure workloads** (databases, caches, brokers, search engines).
  Generated templates are for *your* code. Run infrastructure from its mature
  upstream chart as an entry in this umbrella's `Chart.yaml`
  `dependencies:` block — that upstream chart *is* the best practice.
* **Sidecar containers** (beyond the built-in `troubleshootingContainer`).
  A sidecar is a container in the owning pod, never a new subchart. Add it
  via `initContainers`/custom containers in the owning subchart.
* **Jobs and CronJobs** (schema migrations, batch work). Not yet a supported
  workload kind. Do not fake one with an idling Deployment; add a proper
  Job/CronJob manifest with Helm hooks if you need it before chartpress
  supports it.
* **ServiceAccount + RBAC creation**. Only a `serviceAccountName`
  passthrough is provided. Workloads that need Kubernetes API access should
  get a hand-written, least-privilege Role/RoleBinding — generated RBAC
  tends to be either broken or too broad.
* **External secrets management** (External Secrets Operator, SOPS, CSI
  secret stores). The chart renders plain Secrets from values. Wiring a
  secrets operator is an environment decision, not a chart default; the
  `envFrom` seam is where its output plugs in.
* **Observability CRDs** (`ServiceMonitor`, `PodMonitor`,
  `PrometheusRule`). They hard-fail on clusters without the CRDs installed.
  Add them behind an explicit values flag if your platform has the operator.
* **Egress NetworkPolicies**. The scaffold covers ingress; egress allowlists
  require knowing every dependency the app calls — resolve that against the
  code, then extend `networkpolicy` deliberately.
* **`topologySpreadConstraints`, `priorityClassName`** — cluster-shape
  decisions; passthrough via `affinity`/values additions when you know the
  cluster.
* **Image digest pinning and signature verification** — belongs in the CI
  pipeline and admission control, not in default values.
* **Namespace-level policy** (ResourceQuota, LimitRange, PodSecurity
  admission labels) — namespace and platform concerns; a chart that ships
  them fights its neighbors.

== The one rule

When finishing this chart: **placeholders are replaced, never deleted;
disabled practices are enabled, never removed.** If a practice genuinely
cannot apply to a workload, record why in the subchart's README instead of
silently dropping it.
